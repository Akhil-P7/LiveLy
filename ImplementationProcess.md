## 3. How CMake Wires Everything Together

### 3.1 Build Configuration (`CMakeLists.txt`)

```cmake
# --- Core Settings ---
cmake_minimum_required(VERSION 3.25)
project(LiveLy)
set(CMAKE_CXX_STANDARD 17)

# --- Source Collection ---
# GLOB_RECURSE finds every .cpp under src/ automatically.
# When a new module (e.g., semantic.cpp) is added, it is
# automatically compiled — no manual list maintenance.
file(GLOB_RECURSE SOURCES src/*.cpp)

# --- Build Target ---
add_executable(lively ${SOURCES})

# --- Tests ---
add_test(NAME lexer_hello ...)    # Validates token stream
add_test(NAME parser_hello ...)   # Validates AST generation
```

**Key design decision:** `GLOB_RECURSE` means every new `.cpp` file added to any `src/` subdirectory is automatically picked up at configure time. This makes the build system grow organically as new phases are implemented.

### 3.2 Build Presets (`CMakePresets.json`)

| Preset | Type | Purpose |
|--------|------|---------|
| `default` (configure) | Configure | Ninja generator, Debug mode, Testing ON |
| `default` (build) | Build | Compiles everything under `src/` |
| `default` (test) | Test | Runs all CTest tests with verbose failure output |
| `ci` (workflow) | Workflow | Runs configure → build → test in one command |

**Single command to build and verify everything:**
```powershell
cmake --workflow --preset ci
```

### 3.3 How Tests Validate the Pipeline

```
Test "lexer_hello":
   Runs:  lively examples/hello.lv
   Passes when stdout matches:  BIND (bind).*TYPE_INT (int).*ASSIGN (is)
   → Proves the Lexer correctly tokenizes the source.

Test "parser_hello":
   Runs:  lively examples/hello.lv
   Passes when stdout matches:  ABSTRACT SYNTAX TREE.*VarDecl.*Frontend pipeline completed
   → Proves the Parser generates a valid AST without crashing.
```

## 4. Data Flow Through the Pipeline

### Step 1: Source File is Read

```cpp
// main.cpp
std::string source = readFile(argv[1]);  // "bind x:int is 10;\n..."
```

### Step 2: Lexer Produces Tokens

```cpp
Lexer lexer(source);
std::vector<Token> tokens = lexer.tokenize();
```

The Lexer walks the source string character by character:
- `std::isalpha(c)` → reads identifier or keyword via `readIdentifierOrKeyword()`
- `std::isdigit(c)` → reads number via `readNumber()`
- `std::ispunct(c)` → dispatches to `readOperator()` or `readSymbol()`

Each character sequence produces a `Token{type, value, line, column}`.

**Example:** `bind x:int is 10;` becomes:
```
BIND("bind")  IDENTIFIER("x")  COLON(":")  TYPE_INT("int")
ASSIGN("is")  INT_LITERAL("10")  SEMICOLON(";")
```

### Step 3: Parser Builds the AST

```cpp
Parser parser(tokens);
auto ast = parser.parse();
```

The Parser uses **Recursive Descent** with this precedence hierarchy:

```
parseExpression()
  └── parseEquality()        ==  !=
        └── parseComparison()    >  <  >=  <=
              └── parseTerm()        +  -
                    └── parseFactor()     *  /
                          └── parsePrimary()  literals, variables, (grouped)
```

Top-level dispatch (`parseStatement()`) detects the statement type from the first token:
- `BIND` → `parseVarDecl()`
- `EMIT` → `parseEmit()`
- `CHECK` → `parseIf()`
- `CYCLE` → `parseLoop()`
- `FORGE` → `parseFunction()`
- `YIELD` → `parseReturn()`
- `IDENTIFIER` → `parseAssignment()`

### Step 4: AST is Printed

```cpp
ASTPrinter::printProgram(ast);
```

The `ASTPrinter` uses `dynamic_cast` to identify each node type and recursively prints with indentation. Example output for `bind y:int is 2 + 3 * (4 - 1);`:

```
VarDecl: y : int
  +-- Value:
    +-- BinaryOp: +
      +-- Left:
        +-- Literal: 2
      +-- Right:
        +-- BinaryOp: *
          +-- Left:
            +-- Literal: 3
          +-- Right:
            +-- BinaryOp: -
              +-- Left:
                +-- Literal: 4
              +-- Right:
                +-- Literal: 1
```

This visually proves that `*` binds tighter than `+`, and `(4 - 1)` is correctly grouped.

## 5. Module Independence Guarantees

| Module | Knows About | Does NOT Know About |
|--------|------------|---------------------|
| `token.h` | Nothing | Everything else |
| `lexer/` | `token.h` only | Parser, AST, VM |
| `ast/` | Nothing | Lexer, Parser, VM |
| `parser/` | `token.h`, `ast.h` | Lexer internals, VM |
| `ast_printer.h` | `ast.h` only | Lexer, Parser |
| `main.cpp` | All modules | Internal implementations |

This strict layering means:
1. The Lexer can be unit-tested with just a string input — no Parser needed.
2. The Parser can be unit-tested with a hand-crafted token vector — no Lexer needed.
3. Future phases (Semantic, Bytecode, VM) will only depend on `ast.h` — not on the Lexer.

## 6. Adding a New Phase (e.g., Semantic Analysis)

```
1. Create src/semantic/semantic.h  — declare the class
2. Create src/semantic/semantic.cpp — implement the logic
3. Update main.cpp:
     #include "semantic/semantic.h"
     SemanticAnalyzer analyzer;
     analyzer.analyze(ast);
4. Add a CTest:
     add_test(NAME semantic_hello
         COMMAND lively examples/hello.lv)
5. Run: cmake --workflow --preset ci
```

The `GLOB_RECURSE` in CMakeLists.txt automatically picks up the new `.cpp`. No build file changes needed beyond adding the test.
